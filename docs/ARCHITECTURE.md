# Nebo Stage — Architecture

Nebo Stage is a nationwide (Nigeria) event production and technical services company. This application is its operations platform: a public event production request portal, and an internal system covering inventory, availability, allocation, logistics, maintenance, CRM, quotations and reporting.

This document is the Phase 0 output: what existed, the decisions taken, the target architecture, the module dependency map and the risks. The database design is in [DATABASE.md](DATABASE.md) and the phased plan in [ROADMAP.md](ROADMAP.md).

---

## 1. Discovery findings (Phase 0)

| Question | Finding |
| --- | --- |
| Existing project | `harmanicomputech/nebo` was an **empty repository**. There was no code to preserve. |
| Related code | The session also had `harmanicomputech/claude` (Election Shield, a Laravel 13 USSD election app). It is a different product with a live deadline and was **not modified**. Patterns proven there and worth carrying over are listed below. |
| Framework | Laravel **13.34** (fresh skeleton), PHP **^8.3**. The lockfile resolves Symfony 7.4, so it runs on PHP 8.3 *and* 8.4 (shared hosts often lag). |
| Frontend | Blade + Tailwind CSS v4 + Alpine.js, built with Vite 8. Icons: Lucide via `mallardduck/blade-lucide-icons` (server-rendered SVG, no icon font, works offline). |
| Database | MySQL 8 / MariaDB 10.6+ in production; SQLite in-memory for tests. Every migration must run on both. |
| Authentication | None existed. Built in Phase 1 (session auth, password reset, throttling). |
| Reusable UI | None. A design system of Blade components is built in Phase 1 (`resources/views/components/ui`). |

Patterns carried over from Election Shield (re-implemented, not shared code):

- An append-only **audit log** that never breaks the action being recorded.
- A cached key–value **settings** store editable from the console.
- **Thin controllers**, business logic in `app/Services`, side effects queued.
- Deployability on **shared hosting** (no terminal, no per-minute cron) is kept in mind: prebuilt assets, database queue, no daemons required for core features.

## 2. Key decisions

Each decision is recorded with its reason so it can be revisited deliberately.

| # | Decision | Why |
| --- | --- | --- |
| D1 | Server-rendered **Blade + Alpine** rather than an SPA. | The public portal must be fast and indexable; the internal app is form/table heavy; a single deployable with no Node runtime suits the hosting. API-readiness comes from the service layer (D4), not from the UI. |
| D2 | **spatie/laravel-permission** for RBAC. Permissions are code-defined (`App\Support\Permissions\PermissionCatalog`); roles are data. | Permissions map 1:1 to checks in policies and routes, so they belong with the code. Roles must be editable by administrators. A seeder syncs the catalog idempotently. |
| D3 | **Super Administrator** is granted everything through `Gate::before`, and is a protected system role. | New permissions never need to be granted to it by hand; the last active super admin cannot be removed or deactivated. |
| D4 | Business logic lives in **services** (`app/Services`), validation in **Form Requests**, authorization in **Policies**. Controllers orchestrate only. | Same logic is reused by the web UI, future `/api/v1` (Sanctum), console commands and jobs. |
| D5 | **Users ≠ staff.** `users` are login accounts. `staff` (Phase 4) are people who work events and may or may not log in (`staff.user_id` nullable). | Crew and drivers need to be scheduled without being given accounts. |
| D6 | **Two inventory tracking modes on one catalogue.** `equipment` is the catalogue item (e.g. "Robe MegaPointe"). `tracking_mode = serialized` items have rows in `equipment_assets` (one per physical unit); `tracking_mode = bulk` items have quantities in `stock_levels` per location. | Satisfies both "ML-001 is at the client site" and "we have 1,200 m of 16 A cable" without forcing one model onto the other. |
| D7 | **Asset statuses are a database table with behaviour flags** (`group`, `is_allocatable`, `is_manual`; see D23) and a stable `code`. Engine logic keys off flags and system codes, never off labels. System statuses cannot be deleted. | Admins can add statuses and rename labels without breaking the availability engine. |
| D8 | **Availability is computed from time-windowed holds**, not from a stock counter. Each event has a *hold window* = setup start → breakdown end (+ configurable turnaround buffer). Available(item, window) = in-service units − overlapping holds − maintenance windows − units in non-allocatable status. | The brief requires conflict detection across overlapping dates; a single quantity column cannot express that. |
| D9 | **Double allocation is prevented in the database transaction**, not just in validation: allocation locks the catalogue row (`SELECT … FOR UPDATE`), re-checks overlap, then writes. Serialized assets additionally have a per-asset overlap check. | MySQL cannot express a range-exclusion constraint; serialising writes per equipment item is the reliable alternative. |
| D10 | **Every inventory movement writes an `inventory_transactions` ledger row** (who, what, from/to location, from/to status, qty, reference). Current state is denormalised on the asset for speed; the ledger is the history. | "How did this asset get here?" must always be answerable. |
| D11 | **Workflow statuses** (requests, events, quotations, load lists) are PHP backed enums with an explicit transition map, and every change writes a `status_changes` row (polymorphic: from, to, user, note, time). | Transitions are business rules that need tests; history is required by the brief. Labels are translatable; the set itself changes only with code. |
| D12 | **Configurable option lists** (event types, budget ranges, condition grades, maintenance types, staff roles) live in a `lookups` table (`group`, `key`, `label`, `sort`, `is_active`, `meta`). Services and equipment categories get dedicated tables because other records relate to them. | No hard-coded business values; one admin screen manages them all. |
| D13 | **Reference numbers** (`NEBO-REQ-2026-00001`) come from `ReferenceGenerator`, backed by a `sequences` table locked per key/period. Formats are settings (`{PREFIX}-{YYYY}-{SEQ:5}`). | Gap-free-enough, concurrency-safe, configurable. |
| D14 | **Money is stored as integer kobo** (`bigint`), currency NGN. | No floating-point rounding in quotations and reports. |
| D15 | **Files are private** (`storage/app/private`), stored under random names, served only through an authorising controller. A polymorphic `documents` table links them to any record. Uploads are validated by extension *and* MIME, size-capped. | Customer drawings and contracts must never be web-reachable by URL guessing. |
| D16 | **Soft deletes / archiving** for master data (equipment, assets, customers, users, categories, locations). Historical rows (allocations, ledger, audit) are never deleted. Retiring an asset is a status, not a delete. | Production history must survive. |
| D17 | **Notifications** use Laravel's notification system with the `database` channel (in-app) first. Each notification's `via()` goes through `NotificationChannels::for($user, $type)`, so mail/SMS/WhatsApp are added by configuration later. | The brief asks for in-app first, multi-channel later. |
| D18 | **Public portal and internal app are separated** by route group, layout, middleware and controllers (`App\Http\Controllers\Public\*` vs `App\Http\Controllers\Internal\*`). Public controllers never load inventory models. Public request tracking uses reference + a random token, never sequential IDs. | Requirement 45. |
| D19 | **PWA**: web manifest, service worker and offline page. The service worker caches only static, fingerprinted assets and the offline page; **authenticated HTML and API responses are never cached** (shared/lost devices must not leak operational data). | Installable on phones/tablets for crew and technicians, safely. |
| D20 | Timezone **Africa/Lagos** for display; timestamps stored in UTC. | Single-country operation today; correct if branches span zones later. |
| D21 | `Gate::before` grants Super Administrator only **permission abilities** (`module.action`); policy methods still run for them. | Found in Phase 1 testing: a blanket bypass let a super admin past structural policy rules (deleting a system role, deactivating themselves). The service layer still blocked it, but each rule should hold at every layer. |
| D22 | Fonts are **self-hosted from npm** (`@fontsource-variable/*`) and bundled by Vite. | No third-party request at build or run time, and the fonts work offline in the PWA. |
| D23 | Every asset status belongs to one of eight fixed **groups** (`App\Enums\AssetStatusGroup`: available, committed, out, attention, damaged, lost, retired, unavailable). Dashboards and reports count by group. `is_allocatable` says whether a unit can be allocated; `is_manual = false` marks the statuses that belong to the allocation engine (reserved, allocated, checked out, in transit, deployed, on site). | Admins can add and rename statuses freely, but the code never depends on labels or codes it doesn't own. Only "available"-group statuses can be allocatable. |
| D24 | **Engine-managed statuses can't be touched by hand**: staff can't set them, and an asset in one can't be changed, moved or archived manually. Moving into or out of lost/retired needs `inventory.archive`. | Stops a manual edit from silently breaking an allocation (Phase 5) or quietly writing off kit. |
| D25 | **Condition grades are lookups with behaviour in `meta`**: `blocks_allocation` takes the unit out of availability; `sets_status` moves an in-service unit to that status when the grade is recorded (damaged → Damaged, requires inspection → Under Inspection). | Damaged kit can't be allocated by mistake, and the rule is configurable. |
| D26 | **Bulk stock has two buckets per location**: `available` and `quarantine` (damaged or awaiting inspection). Only `available` counts. Write-offs and stock counts require a reason; stock can never go negative (row locks + checks). | Mixed-condition cable stock without serialising every cable. |
| D27 | **Asset tags** come from the shared `sequences` counter per prefix (`ML-001`) and skip tags typed by hand. Each asset also has an opaque **ULID `qr_token`**; QR labels encode `/app/scan/{token}`, which needs sign-in. QR codes are rendered as SVG by bacon/bacon-qr-code (pure PHP). | Labels leak nothing if photographed, tags stay unique, and it runs on shared hosting without Imagick. |
| D28 | **Uploaded images are decoded and re-encoded with GD** (max 1600px, WebP), stored on the private disk and served through an authorising route. | Strips EXIF/GPS, rejects disguised files, keeps pages light. |
| D29 | **"Available now"** (Phase 2) = allocatable status + non-blocking condition (serialized) or the available bucket (bulk), computed in SQL (`Equipment::availableUnitsSql()`). Phase 5 adds date-window holds on top of this; it does not replace it. | Filtering and sorting by availability in the database, with no full-fleet loads. |
| D30 | Lookups are read through `App\Support\Lookups`, a **container-scoped** memo, not a static cache. | Static caches go stale across tests and long-running workers (and on MySQL, auto-increment IDs don't roll back between tests). |
| D31 | **Public form protection without a CAPTCHA**: per-IP throttling (5/min, 20/h), a honeypot field, an encrypted form-start time (≥3 s, ≤24 h), and a one-time `submission_key` that makes resubmits idempotent. | Stops scripts and double clicks without friction for real customers; Turnstile can be added later if spam gets through. |
| D32 | **Customer matching**: normalised email, then E.164 phone (`App\Support\PhoneNumber`, Nigerian formats). A match with a different contact name or company sets `needs_review`; nothing is overwritten or auto-merged. | Returning customers aren't duplicated, and shared office emails/phones don't silently merge different people. |
| D33 | **Customers see 5 public stages** (`RequestStatus::publicStage()`), never the 15 internal statuses, notes, staff names or documents. Tracking uses an unguessable ULID token, or reference + email, throttled. | Requirement 45 and §49 (no internal terminology). |
| D34 | **Uploads are checked by content**: an extension allowlist plus the MIME type sniffed from the bytes with finfo, or the file signature for DWG/DXF. Files are stored under random names; images preview inline, everything else downloads, with `nosniff` and a sandboxing CSP. | A script renamed `.pdf` is rejected, whatever the client claims. |
| D35 | **Form datetimes are entered in Lagos time and converted to UTC** in the form request before validation and storage. | Avoids an hour's drift in setup times (D20). |
| D36 | **Email is sent only when a real mailer is configured** (not `log`/`array`), queued, and failures never lose the request. In-app notifications go to users with `requests.manage`. | §15: "send confirmation when email functionality is configured". |
| D37 | **Event lifecycle**: Planning → Confirmed → In Preparation → In Progress → Completed, plus On Hold and Cancelled (reasons required). Completed and Cancelled are read-only except notes. `EventStatus::holdsResources()` decides which events hold equipment and crew. | Explicit, testable transitions (D11); Phase 5 availability counts only active events. |
| D38 | **Request → event conversion** is allowed once, only for won requests; it copies customer, type, services, requirements and documents, and an Approved request moves to Production Scheduled. | One source of truth per production, with no lost history. |
| D39 | **Crew double-booking is blocked** across overlapping hold windows of active events, unless a manager overrides it with a reason, which is recorded in the audit log. | Brief §54 (no invalid scheduling), with room for real-world exceptions. |
| D40 | **Assigned-only access**: `events.view_assigned` (Crew, Technician) sees events where the user is the project manager, the production manager, or on the team through their staff profile. It is enforced in `EventPolicy` and in `Event::scopeVisibleTo()` for lists, the calendar and search. | Crew see their own work only. |
| D41 | **The calendar is built by `ProductionCalendar`** in Lagos time; each event shows on every day of its hold window labelled Setup / Show / Breakdown (text, not only colour). On phones, month cells show a count and phase bars that link to the day view. | Readable and accessible on every screen; Phases 5 and 6 add entry sources. |
| D42 | **Navigation items accept a permission or a closure**, so policy-based visibility (events for assigned-only users) needs no special cases. | Keeps `Navigation` declarative. |
| D43 | **Availability is computed, never stored.** `AvailabilityService` takes the serviceable pool (status group available / committed / out with a non-blocking condition), subtracts units on *active* allocations of other events whose hold window overlaps, and subtracts units returned by `AvailabilityBlocker` implementations (`AvailabilityService::BLOCKERS`; Phase 6 adds maintenance). Bulk: owned `available` bucket − overlapping held quantities. | One rule for the event workspace, the availability grid, the calendar flags and the allocation check; future-dated bookings don't depend on today's status. |
| D44 | **Hold window** = event `setup_starts_at → breakdown_ends_at`, widened on both sides by the `availability.buffer_hours` setting (default 0), copied onto each allocation (`hold_starts_at`, `hold_ends_at`). Changing the event's dates re-windows its allocations through `AllocationService::rewindow()`, which refuses the change if a held unit would clash. | Overlap queries stay on indexed allocation columns; a date change can't silently create a double booking. |
| D45 | **Allocation is race-safe:** the equipment row is locked (`lockForUpdate`) and availability is re-checked inside the transaction before any allocation is written. | MySQL has no exclusion constraints (D9); two coordinators can't take the last unit together. |
| D46 | **Allocation states**: reserved → checked_out (on dispatch) → returned, or reserved → released. Only reserved items can be released; checked-out items must be checked in. The asset's engine status follows the state (allocated while reserved, checked out, deployed when the event is in progress, then the return outcome). Cancelling or completing an event is refused while anything is checked out, and releases what is still reserved. | Physical kit and the records can't drift apart. |
| D47 | **Requirements are per catalogue item**; the analyzer reports required, allocated, free, shortage, the clashing events, units that exist but aren't serviceable, and alternatives with free units from the same category family (parent and siblings). | Brief §20: shortages and alternatives without hard-coded substitutions. |
| D48 | **Load list** (`NEBO-LL-…`): one per event, synced from its reserved allocations; each line goes Pending → Picked → Loaded → Checked. Dispatch needs every line checked and checks everything out in one transaction (ledger `checked_out`). A printable load sheet has signature lines. | Brief §21 load-out with an auditable hand-over. |
| D49 | **Check-in** records per-unit outcomes (returned, missing, damaged, needs inspection, needs maintenance) or per-bulk-line counts that must add up. Missing serialized units become Lost; damaged ones get the damaged condition (and status via D25); missing bulk is written off and damaged bulk moved to quarantine. Issues notify users with `inventory.manage`. | Losses and damage enter the ledger and inventory immediately. |
| D50 | **Scheduled maintenance blocks availability** through `MaintenanceBlocker` (an `AvailabilityBlocker`): an open job with a window takes that unit out of every overlapping availability check, so it can't be allocated or have an event moved onto it. A window can't be scheduled over a unit's active booking. Units already out for maintenance are excluded by their status (attention group). | Planned servicing and event bookings never collide, in either direction. |
| D51 | **Maintenance job lifecycle**: Reported → Scheduled → In Progress → Completed, or Cancelled (reason required); Reported/Scheduled may complete directly for on-the-spot fixes. History in `status_changes`. A fault report can take an in-service unit out of service at once (Maintenance Required); starting work sets Under Maintenance; completing records the condition (and a condition report) and returns the unit to Available (ledger `repaired`) unless the condition still blocks allocation or another job keeps it out; cancelling returns it if nothing else does. Work can't start on a unit that is booked or at an event (engine-managed status). | Every status change goes through `AssetService` and the ledger (D24); booked kit is never silently pulled. |
| D52 | **Schedules are per unit and type** (unique), with an interval in days; "apply to every unit of an item" creates one per unit. Completing a job advances its schedule (or the unit's schedule of the same type); the asset's `next_maintenance_due_on` mirrors its earliest active schedule. A daily digest (`nebo:maintenance-reminders`, 07:00 Lagos) notifies `maintenance.manage` users once when a schedule enters the `maintenance.reminder_days` window and weekly while overdue, skipping schedules with an open job. | Each unit has its own history and due date; reminders don't nag daily. |
| D53 | **Condition history** is an append-only `condition_reports` table fed by inspections (with photos as documents on the report), check-ins and completed jobs. Check-in outcomes damaged / needs inspection / needs maintenance open a job automatically (unless one is open). Inspections are allowed for `inventory.update` or `maintenance.manage`; technicians (`maintenance.view_assigned`) see only jobs assigned to their staff profile. | Brief §26–27: inspections, damage photos and traceable condition over time. |
| D54 | **Trips** (`NEBO-TRP-…`) go to a venue (outbound), back to base (return) or between sites (transfer, no event needed). A trip has a vehicle, a driver, crew and a **manifest** of the event's allocations; an allocation can be on one outbound and one return trip (cancelled trips release it). Outbound manifests take reserved or checked-out items; return manifests only checked-out ones. | Ties the physical movement to the exact kit, without a second inventory model. |
| D55 | **Clashes**: a vehicle can't be on two trips whose scheduled windows overlap, or be booked while out of service or retired, and a booked vehicle can't be taken off the road or archived. A driver or crew member on an overlapping trip needs an override reason, which is audited (same pattern as D39). | Vehicles are a hard constraint; people sometimes legitimately do two short runs. |
| D56 | **Trip lifecycle**: Planned → Loading → In Transit → Arrived, or Cancelled (reason required). Leaving needs a vehicle and a driver and every manifest item dispatched from the load list. Departure moves units to In Transit (ledger `in_transit`); arriving at a venue moves them to On Site, or Deployed if the event is live (ledger `delivered`, with who received it); a return arrival leaves them Checked Out awaiting check-in. An event going live doesn't mark units still on the road as Deployed. | The asset page always says where the kit physically is. |
| D57 | **Drivers and trip crew** (`logistics.view_assigned`, given to Crew) see only their own trips, on the logistics page, dashboard, calendar and search, and can mark them loading, departed and arrived. Planning, editing and cancelling need `logistics.manage`; the fleet needs `logistics.view` / `vehicles.manage`. | Drivers update status from their phones; they don't see the whole schedule. |
| D58 | Columns named `notes` are reserved for the polymorphic notes relation (`HasNotesAndDocuments`); free-text fields on such models use other names (`instructions`, `remarks`). | A `notes` column silently shadows the relation. |
| D59 | **Tap feedback everywhere** (`resources/js/app.js`): on touch screens every link and button dims the moment it is pressed; a submitted form marks the tapped button busy (spinner, disabled) and ignores repeat submissions; a same-site link tap marks the link busy and ignores repeat taps; a progress bar runs until the next page loads. Buttons are disabled a tick after submit so the tapped button's `name=value` is still sent. Busy state clears on back/forward navigation and after 15 s as a fallback. Opt out with `data-no-busy` (file downloads). | Slow mobile networks: people tap again when nothing seems to happen, creating duplicate records. |
| D60 | **Quotations** (`NEBO-QUO-…`): Draft → Sent → Accepted / Declined / Expired, or Cancelled; Sent, Declined and Expired can be **revised** back to a draft (revision number +1). `quotations.manage` prepares drafts and records answers; only `quotations.approve` can **approve and send**. Lines are quantity × days × unit price in sections; the server recomputes subtotal, discount (kept as entered, applied up to the subtotal), VAT (basis points, default from settings) and total on every save — the browser's figures are only a preview. Sending moves a linked request to Quotation Sent and acceptance moves it to Confirmed when the workflow allows. A daily `nebo:expire-quotations` marks overdue quotations Expired. | Sales can't send unapproved prices, and no total can be tampered with from the form. |
| D61 | **Production packages** are priced bundles of lines that prefill or extend a quotation; quotations copy the lines, so editing or archiving a package never changes a quotation. Equipment has an internal **day rate** (edited only by `inventory.costs`) that fills equipment lines. | Fast, consistent quoting without hard-coded prices. |
| D62 | **Customer quotation link** `/q/{ulid}`: the one public page that shows a quotation, by its unguessable token (throttled, `noindex`, no referrer). It shows only the lines, totals, terms and company details we send; drafts and cancelled quotations 404; revising issues a new token so an old copy can't be accepted; acceptance needs a name and an explicit tick, and is recorded with the answer in the timeline and notified to approvers. This is the only exception to "public controllers never load pricing" (D18). | Customers accept from their phone without an account; nothing internal leaks. |
| D63 | **CRM**: customers get a type (lookup), city and state; `remarks` replaces the `notes` column (D58). Profiles flagged by matching (D32) show likely duplicates; staff either mark them checked or **merge** a duplicate into the kept profile, which moves requests, events, quotations, notes and documents, fills blanks, archives the duplicate and audits the move. | De-duplication stays a human decision, with nothing lost. |
| D64 | **Charts are server-rendered HTML/CSS** (`x-chart.columns`, `x-chart.bars`, `App\Support\Charts`), no chart library: they work offline in the PWA, print, keep real-size text on phones and need no JSON endpoints. Colours are the validated categorical order (blue `#2a78d6`, orange `#eb6834`, aqua `#1baf7a`; checked with the colour-blind validator on the white card surface); text never wears the series colour. Columns ≤ 24 px with a rounded data end and 2 px gaps between stacked segments; ranked bars carry the value at the tip; a legend for two or more series; every chart has a "View as table" and a hover/focus tooltip (text only). The brand red is not used for data so it never reads as an alarm. | Accessible, consistent charts with no third-party code. |
| D65 | **Reports** (`ReportService`, `/app/reports/{report}`): utilisation (unit-days booked ÷ unit-days owned; released holds don't count), events and request pipeline, maintenance (volume, turnaround, cost with `inventory.costs`), logistics (trips, vehicle use, on-time within 30 min), inventory (fleet by status and category, value with costs) and commercial (needs `reports.financial`). One filter row with period presets or a custom range in Lagos time. CSV export needs `reports.export`, is audited, starts with a UTF-8 BOM, and prefixes cells starting with `= + - @` with `'` so spreadsheets don't run them as formulas. | Decisions from live data; exports can't smuggle spreadsheet formulas. |
| D66 | **Content-Security-Policy** on every response (`SecurityHeaders`): scripts, styles, fonts, images, connections, workers and form posts only from this site; no framing; no plugins; `upgrade-insecure-requests` over HTTPS. Alpine needs `'unsafe-eval'`, accepted because there are no inline scripts or handlers (a test fails if any `<script>` block or `on*=` attribute appears in a view) and no user-supplied HTML is ever rendered. Style attributes need `'unsafe-inline'` for styles only. Responses that set their own policy (document downloads, D34) keep it. Page actions use `data-action` (print, reload, back) instead of inline handlers. | Defence in depth against injected script; caught three inline handlers that would have silently broken. |
| D67 | **Production readiness**: `nebo:check-production` fails on debug mode, a non-HTTPS URL, insecure cookies, pending migrations, missing permissions, no active super admin, demo data, unwritable folders or unbuilt assets, and warns on a log mailer, placeholder company email or a sync queue. In production with an https `APP_URL`, links are forced to https. The scheduler drains the queue every minute, so one cron line runs everything on shared hosting. Hashed build assets are cached for a year and dotfiles are denied in `.htaccess`. See `docs/DEPLOYMENT.md`. | A misconfigured server is caught before customers are, without needing a daemon. |
| D68 | **Brand logo**: the supplied artwork (`resources/brand/nebo-stage.png`, black ink on transparent) is the source of truth. It is traced to SVG (matches the artwork to 1 px in 61k) as ink and white versions of the full logo and of the mark (`public/images/brand`), served as cached image files (not inlined: 27 KB each) through `<x-ui.logo dark? compact?>`. `scripts/generate-icons.php` builds the PWA/Apple/favicon icons (white mark on ink `#1A1A1A`, rounded or full-bleed maskable), `favicon.ico`, and PNG logos for emails (most mail clients block SVG). The service worker caches the brand files; bump its `VERSION` when they change. | One artwork, every surface; the monochrome logo reads on light and dark backgrounds. |
| D69 | **No-terminal hosting** (DirectAdmin/cPanel): `scripts/build-directadmin.sh` builds a zip with `nebo/` (app, `vendor` without dev packages, no tests) beside `public_html/` (the `public` folder; `deploy/directadmin/index.php` points to `../nebo` and calls `usePublicPath`). The first visit copies `.env.directadmin` to `.env` with a fresh `APP_KEY`; with `NEBO_INSTALLER=true` every page leads to `/install` (`RedirectToInstaller`) until `storage/app/installed.lock` exists. The installer checks the server, tests the database connection, writes `.env` (`Installer::writeEnv`, quoting-safe), then runs `InstallSteps` one step per request (migrate, reference data, admin, each demo seeder, `HistoryDemoSeeder` in batches of 3), each retryable, the page reloading itself (meta refresh: no inline script). Settings → System (`system.manage`) shows `ProductionChecks` and applies an uploaded update (`SystemUpdater`: migrate, reference data, clear caches). `BackgroundTasks` runs the daily jobs once per Lagos day after their time (deduplicated in the cache) and drains the queue; the scheduler calls it every minute (`nebo:tick`) and, with `NEBO_WEB_CRON=true`, `RunBackgroundTasks` calls it after a response at most once a minute. | Owners can install, test with demo data and update without SSH or cron; nothing runs long enough to hit shared-hosting time limits. |
| D70 | **Phone app shell**: below `lg` the internal app is laid out like a native app; from `lg` up it is unchanged. A dark top bar (`partials/mobile-top-bar`) shows the logo on top-level screens and a back arrow plus title on detail screens (history back within the app, else the section's list from `Navigation::mobile()`), with full-screen search and notifications. A bottom tab bar (`partials/mobile-tab-bar`) holds four role-aware tabs (`Navigation::TAB_PRIORITY`, first four the user can open) and **More**, a bottom sheet with every module, the account, install and sign-out. Shared components adapt instead of each page: `<x-ui.table>` rows become labelled cards (`data-stack`, labels copied from the headings by `app.js`; opt out with `:stack="false"`), filter forms marked `data-filters` collapse to the search box and a Filters button with an applied-count, modals and confirmations become bottom sheets, stat tiles are compact and two-up, page headers drop breadcrumbs and stretch their actions, and fields are 16px so iOS doesn't zoom. The phone rules are unlayered CSS so they win over utility classes. | The PWA is used mostly on phones by crew, drivers and technicians; it should feel like an installed app, without a second set of pages to maintain. |
| D71 | **Sample data without labels.** The sample seeders use realistic names, companies, emails, phone numbers and SKUs (`NS-…`), with no "demo" text. While they run inside `SampleData::record()`, an `eloquent.created` listener notes every created row (table, key) in `sample_records`, in order. **Settings → System → Clear sample data** (`system.manage`) deletes those rows newest first in one transaction, removes sample users' role pivots, restarts reference counters whose tables are now empty, and is audited. People's own records that depend on sample rows through a restricting key (found transitively from the schema's foreign keys) are listed and only removed when the person confirms the second button; it refuses if no non-sample active Super Administrator would remain.
